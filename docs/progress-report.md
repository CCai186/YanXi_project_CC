## 一、项目概述

AI 语音通话助手，在电话呼叫机主之前代接来电，实现智能化的来电筛选与处理。基于 LangChain/LangGraph 多智能体框架，结合 Faster-Whisper 语音识别 + DeepSeek V4 Pro LLM + ChromaDB RAG 知识库。

---

## 二、v1 原有架构 → v2 融合升级

### v1 原始架构（我们的项目）

v1 是一个**四分类 + LLM 动态生成**的简单架构，从零搭建：

```
麦克风(VAD) → Whisper STT → LangGraph 三节点调度
                                ├── 诈骗检测 (ScamDetector: RAG + LLM)
                                ├── 意图分类 (LLM: business/urgent/general)  
                                └── 处理分发 (BusinessHandler / UrgentForwarder / GeneralReply)
```

- 分类：4 类（诈骗/业务/紧急/普通）
- 决策：每次必调 LLM（3 次 API 调用/通电话）
- 回复：LLM 动态生成（不稳定）
- 录音：VAD 音量检测（不可靠，需要反复调阈值）
- 状态：4 种机主模式（free/busy/dnd/driving）+ 多轮上下文保持

### YanXi-KCN 参考架构（同组项目）

YanXi-KCN 是一个**16 分类 + 预设规则**的成熟架构，有 1550 条真实通话记录索引：

```
麦克风(空格键) → Whisper STT → Pipeline
                                  ├── CallRouter (关键词 + RAG 辅助)
                                  ├── Agent Factory (为每种类型创建对应 Agent)
                                  └── HybridRAG (向量检索 + 知识图谱 + RRF 融合 + 重排)
```

- 分类：**16 类**细分（外卖配送、快递取件、推销、诈骗、熟人问候、家人、领导、同事、客户、打车、银行、游戏推广、面试通知、诈骗风险、无意义、其他）
- 决策：**三级分类**（关键词→RAG→LLM，大部分来电靠关键词，省 token）
- 回复：**16 种预设规则表**，每种类型有固定 action+response，更稳定
- 录音：**空格键控制**，100% 可靠
- RAG：**Hybrid RAG**（向量 + 知识图谱 2836 节点 + Louvain 社区检测 + RRF 融合 + 重排）

### v2 融合策略：取两者之长

**保留我们的**（因为做得好或必须保留）：
- 机主状态系统（free/busy/dnd/driving）— YanXi-KCN 只有上课/下课二值
- 多轮对话上下文保持 — YanXi-KCN 是一次性分类
- DeepSeek V4 Pro 作为 LLM — 我们已有的 API
- Faster-Whisper large-v3 GPU — 比他们的 small 模型更准
- 诈骗检测的 RAG 知识库（含内置样本 + 推理分析）

**引入 YanXi-KCN 的**（因为更成熟）：
- 16 种来电类型定义 + 预设处理规则表（替代我们的 4 类粗分）
- 三级分类器：关键词→RAG→LLM（替代每次必调 LLM）
- 空格键录音控制（替代不可靠的 VAD）
- 无意义文本检测（过滤 STT 的杂音输出）
- RRF 融合 + 重排器（为后续知识图谱做准备）
- Pipeline + Factory 架构思路（简化调度器）

**融合后 v2 的最终架构**：

```
麦克风(空格键) → Whisper large-v3 STT → 无意义检测
    ↓
三级分类器 (关键词 → RAG → LLM)     ← 来自 YanXi-KCN
    ↓
16 类处理规则 × 4 种机主状态 = 64 种响应组合  ← 两者融合
    ↓
动作: reject / forward / proxy / record / ask
    ↓
多轮上下文保持 + 重分类              ← 我们原有的
```

**对比总结**：

| 维度 | v1 (我们的) | YanXi-KCN | v2 (融合后) |
|------|-----------|-----------|------------|
| 分类粒度 | 4 类 | 16 类 | **16 类** ← KCN |
| 分类方式 | LLM 必调 | 关键词→RAG→LLM | **三级** ← KCN |
| 处理规则 | LLM 动态生成 | 16 种预设表 | **16 种 × 4 状态** ← 融合 |
| 录音 | VAD 阈值 | 空格键 | **空格键** ← KCN |
| 机主状态 | 4 种模式 | 上课/下课 | **4 种模式** ← 我们的 |
| 多轮对话 | 上下文保持 | 一次性 | **上下文+重分类** ← 我们的 |
| 无意义检测 | 无 | 有 | **有** ← KCN |
| RAG 增强 | 向量检索 | 图+向量+RRF | **向量+RRF+重排** ← 融合 |
| LLM 调用 | 3次/通 | 0-1次/通 | **0-1次/通** ← KCN |
| STT 模型 | large-v3 | small | **large-v3** ← 我们的 |

## 三、已实现的核心功能

| ⚠️ 疑似诈骗 | reject 拒接 | ~90% (关键词) |

| 🚗 打车到达 | proxy 代接对话 | ~85% (关键词) |
| 📢 推销电话 | reject 拒接 | ~85% (关键词) |
| 🎮 游戏推广 | reject 拒接 | 待测试 |
| 👨‍👩‍👧 家人来电 | ask 追问/forward | ~70% (关键词) |
| 👔 领导来电 | ask 追问/forward | ~70% (关键词) |
| 🤝 熟人问候 | ask 追问 | ~80% (关键词) |
| 💼 同事协作 | record 记录 | 待测试 |
| 🤵 客户来电 | record 记录 | 待测试 |
| 🏦 银行来电 | record 记录 | 待测试 |
| 📋 面试通知 | forward 转接 | ⚠️ 易误判为诈骗 |
| ❓ 无意义输入 | ask 重新问 | ~95% |
| 📞 其他来电 | ask 追问 | 兜底 |

### 2.3 三级分类器
- **第一级：关键词匹配** — 免费、毫秒级，覆盖大部分常见来电（10/12 测试用例命中）
- **第二级：RAG 检索** — 关键词不确定时触发，从知识库检索相似案例辅助判断
- **第三级：LLM 增强** — 前两级都不确定时调用 DeepSeek，占测试用例的 ~15%

### 2.4 机主状态管理
| 状态 | 触发方式 | 行为 |
|------|---------|------|
| 空闲 (free) | 默认 / `/free` | 诈骗拒接，朋友→转接，外卖→代接 |
| 忙碌 (busy) | `/busy 开会 30分钟` | 只转接紧急+亲属，其余代接 |
| 免打扰 (dnd) | `/dnd 睡觉了` | 几乎不转接，全代接/留言 |
| 开车 (driving) | `/driving` | 全代接，告知"机主在开车" |

### 2.5 多轮对话
- 首轮分类 → 追问身份/来意 → 业务对话 → 信息收集 → 生成卡片
- 上下文保持：后续轮次自动跳过风险检测，直接继续对话
- 重分类：每轮新消息重新走分类器（避免"送外卖的"被当成普通来电）

### 2.6 RAG 知识库
- 数据：40 条内置样本（30 条诈骗 + 10 条正常通话）
- 检索：语义检索 (ChromaDB+BGE) 优先，关键词匹配兜底
- 数据集：支持 HF 镜像下载 TeleAntiFraud-28k，或本地 Kaggle 导入

## 三、技术架构

```
麦克风 → [空格键录音] → Whisper STT → 无意义检测
    ↓
三级分类器 (关键词 → RAG → LLM)
    ↓
16类处理规则 + 机主状态 → 动作决策
```

## 四、已知问题

### 4.1 分类器问题
| 问题 | 严重度 | 说明 |
|------|-------|------|
| "面试通知"误判为诈骗 | 中 | "恭喜通过面试"含"恭喜"被诈骗关键词命中 |
| 关键词冲突 | 中 | 多义词可能被错误分类（如"案件"既可指诈骗也可指法律业务） |
| RAG 偏向 | 中 | 知识库诈骗样本占 75%，正常来电检索也可能返回诈骗案例 |
| sentence-transformers segfault | 高 | 加载 BGE 模型时与 CUDA PyTorch 冲突，已改懒加载但首次检索仍可能 crash |

### 4.2 对话质量问题
| 问题 | 严重度 | 说明 |
|------|-------|------|
| 业务对话重复提问 | 中 | 对方已说过"我是送外卖的"，下一轮还问"哪家外卖" |
| JSON 输出不稳定 | 中 | LLM 的 JSON 偶尔格式错误，导致信息收集不完整 |
| 结束条件太激进 | 低 | 对方说"放门口"就结束，但可能还有"冷冻食品快点拿"没说 |
| 空闲模式回复太正式 | 低 | 有时候还是偏客服腔 |

### 4.3 系统稳定性
| 问题 | 严重度 | 说明 |
|------|-------|------|
| CUDA/PyTorch 兼容性 | 高 | sentence-transformers + CUDA PyTorch 偶发 segfault |
| Windows 编码问题 | 低 | GBK 终端无法显示 emoji，但不影响功能 |
| HuggingFace 依赖网络 | 中 | 虽然设了镜像，但首次下载模型仍需网络 |

## 六、下一步工作建议

### 立即修复
1. **面试通知误判**：在"scam_risk"关键词中加入排除词，包含"面试/HR/入职"时不判为诈骗
2. **sentence-transformers segfault**：禁用 RAG 的语义模式，纯用关键词检索；或换用 CPU-only 的 sentence-transformers
3. **业务对话重复提问**：在 business_handler prompt 中加入对话历史，让 LLM 知道前面问了什么

### 中期优化
4. **分类优先级调整**：面试/家人/领导关键词优先于诈骗关键词中的"恭喜/领导"等歧义词
5. **知识库平衡**：增加正常通话样本到 50+ 条，减少 RAG 偏向
6. **对话自然度**：用 few-shot 示例训练 LLM 生成更口语化的回复

### 长期规划
7. **知识图谱**：从 YanXi-KCN 移植 NetworkX 知识图谱 + Louvain 社区检测
8. **RRF 融合**：向量检索 + 图谱检索多路融合提升准确率
9. **声纹识别**：识别机主本人的语音命令
10. **真实通话接入**：对接电话线路，实现真·代接
